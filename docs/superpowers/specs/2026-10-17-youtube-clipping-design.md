## 目标与体验

在普通 YouTube 视频页点击 Clipping Anything，选择「YouTube 视频」，把视频信息和页面已显示的文字记录保存进 Obsidian。打开笔记的阅读视图后，在笔记顶部播放该视频；点击字幕时间跳转**笔记内同一播放器**，播放进度反向高亮字幕。视频随笔记滚动离开视野时继续播放，回到顶部仍是同一播放会话。用户可以从专用模式切换到「网页裁剪」，也能返回。

项目的长期方向是跨平台媒体剪藏；本次只交付 YouTube 标准视频页的专用流程。已稳定的 B 站和通用网页剪藏行为保持兼容。

## 决策与依据

- **专用 YouTube 流程，少量共用接口。** 路由、页面采集、弹窗与播放器适配独立；复用已存在的仓库列表、保存入口和统一视觉规范。这样可单独回归 B 站流程。
- **只读取当前页面实际呈现的文字记录。** 采集时间和文本，不调用未公开字幕接口，也不把浏览器通用网页提取器的网络字幕结果当作专用模式数据。文字记录未打开时，提示用户在 YouTube 页面点击「显示文字记录」并刷新；不自动操作页面。无可见字幕时仍可保存视频信息，并在笔记里明确标注无字幕。
- **笔记内同等体验是发布门槛。** 字幕时间不得新开 YouTube 标签页；笔记内播放器必须响应跳转，并由其真实播放进度高亮字幕。只有扩展端和 Obsidian 端在真实环境通过验收才发布专用功能。
- **使用 YouTube 官方嵌入播放器接口。** 先验证 Obsidian 桌面 WebView 中的嵌入加载、IFrame API 就绪、`seekTo`、`getCurrentTime`、播放状态和来源标识。无法满足时停在技术验证并修订方案，不以第二个浏览器播放器冒充笔记内联动。

备选方案：沿用网页模式的 `defuddle` 字幕抓取，覆盖范围可能更大，但依赖页面内部数据和网络请求，与本次「稳定优先、只读显示的文字记录」决策不符；复用 B 站的 Electron 内部视频控制方式也会把两种平台协议耦合起来，因此不作为 YouTube 主路径。

## 范围与界面

- 首版专用路由仅匹配 `https://www.youtube.com/watch?v=<有效视频 ID>`。播放列表中的标准 watch 视频仍按当前 `v` 参数处理；`youtu.be` 重定向到 watch 后生效。Shorts、直播页、音乐站、嵌入页和其他域名继续走网页模式，并在文档列为后续适配。
- 专用弹窗与现有弹窗保持相同外框尺寸和品牌；展示标题、频道、来源网址、字幕状态、条数、预览和目标仓库。提供刷新、保存到 Obsidian、复制 Markdown，以及与网页模式双向切换。字幕缺失时「保存视频信息」可用，字幕下载或依赖字幕的操作禁用并说明原因。
- 复用设置页的仓库列表；YouTube 专用设置仅加入本次确需的目标目录和笔记命名，避免照搬 B 站 AI、评论或多字幕轨设置。默认保存使用 Obsidian URI 的 `new` 动作和 `clipboard` 参数；不传 `append` 或 `overwrite`。若以后增加 REST 直写，应单独设计和验证。

## 数据流与笔记格式

1. 弹窗记录活动标签 ID、URL 与当前视频 ID，向该标签的专用 content script 请求快照。若 YouTube 单页导航使页面 ID 与请求 ID 不同，停止保存并提示刷新。所有快照字段都绑定同一视频 ID。用户点击「保存」或「复制 Markdown」时，再次检查原标签仍存在、仍是活动标签且 URL 的视频 ID 与快照一致；否则禁止动作并要求重新采集，防止预览滞留后保存错视频。
2. 采集页面可见的标题、频道、视频 URL、简介摘要和当前打开的文字记录。识别 YouTube 文字记录的已知 DOM 结构；每条字幕必须有可解析的非负起始时间和非空文本。保留原顺序；只去除由重叠 DOM 选择器产生的**同一视频 ID、同一起始时间、同一文本**的重复行，保留不同时间的重复文字；跳过无效行，不自行生成、翻译或补全字幕。章节只有在页面明确提供、且可绑定当前视频时才保存。
3. 生成 Markdown：Frontmatter 标记 `clip_platform: youtube`、`youtube_id`、来源 URL、标题和剪藏时间；正文先放 `https://www.youtube.com/embed/<id>?enablejsapi=1` 的 iframe，再放可选简介、可选 `## 章节` 和 `## 字幕`。字幕行统一为 `` `MM:SS` 文本 `` 或小时制 `` `HH:MM:SS` 文本 ``，沿用现有解析器可识别的格式。无字幕时 `## 字幕` 下写明确提示，不生成虚假的时间戳或指向 YouTube 网页的字幕链接。
4. 保存前显示 Markdown 预览。每次剪藏创建独立笔记：文件名由安全化标题、视频 ID、UTC 时间和随机标识组成；重复剪藏产生新文件，并在弹窗显示将创建的完整路径。若随机标识生成失败则阻止保存；URI 不带 `append`/`overwrite`，绝不主动覆盖或追加已有笔记。点击保存时先把**当前预览对应的完整 Markdown**写入系统剪贴板，等待写入成功后立即发出带 `clipboard` 的 Obsidian URI，并提示「已复制笔记内容，正在交给 Obsidian；请在目标仓库确认新笔记」。这会替换用户原有剪贴板内容，弹窗须说明；剪贴板写入失败时不打开 URI，保留预览并提示手动复制。URI 是单向调用，扩展不能检测 Obsidian 内部的同名文件处理结果，因此不声称已写入，也不显示未经证实的冲突提示；用户可按显示的目标路径核对，未创建时重新生成文件名再试。标题、路径、Frontmatter 和正文都需正确转义，避免页面文本破坏 Markdown 或写到意外路径。

## Obsidian 播放器适配

- 配套插件仅接管精确匹配的 `www.youtube.com/embed/<11 位视频 ID>` iframe，并验证笔记 `youtube_id` 与嵌入 ID 一致；B 站识别与控制逻辑继续独立。只在桌面版 Obsidian 的阅读视图生成顶部播放器和滚动字幕；编辑视图保留 Markdown。阅读视图渲染出的原 iframe 先被移除并替换为占位符，再在顶部创建唯一的 YouTube iframe；整篇笔记每个阅读视图只有这一个播放器和一个 IFrame API 实例，不在原位置另留可播放 iframe。
- 以官方 IFrame Player API 作为 YouTube 适配层：播放器准备好后调用 `seekTo(seconds, true)`，定时读取 `getCurrentTime()` 选中最后一个起始时间不晚于当前进度的字幕。点击时间不改变暂停或播放状态，不新开标签页。保持播放器 DOM 实例不因滚动而重建；笔记切换、视图销毁和插件卸载时释放计时器、事件监听和播放器。
- 字幕区和笔记正文中的同视频时间戳都调用这一会话；不同视频 ID 的链接保留正常行为。现有解析器在 `## 字幕` 节内接受独立行 `` `MM:SS` 文本 ``、`` `HH:MM:SS` 文本 ``，也接受同格式的旧链接时间戳；实现时为 YouTube 新增同视频校验和点击接管，并用测试锁定这一格式与正文时间戳行为。尚未就绪、禁止嵌入、网络错误或 API 不可用时给出具体状态，避免误报「已跳转」。
- Chrome 扩展的网络规则不会自动应用到 Obsidian。技术验证必须确认桌面嵌入请求提供 YouTube 要求的应用来源标识，且 Obsidian 的 CSP、iframe 沙盒与 API 消息通信允许播放和进度读取；不得用伪造 `youtube.com` 来源来绕过限制。若这些条件无法可靠满足，先修订设计并告知用户，再决定是否实现替代交互。

## 验证与发布

先做一个仅用于技术验证的临时 Obsidian 仓库样例笔记，确认 YouTube iframe 在桌面版可播放、API 可读进度、暂停时点字幕只跳转不自启、播放时高亮推进、滚动离开后不重置、重新打开笔记能重建会话。验证通过再做完整扩展 UI 与保存流程。

自动检查覆盖：URL 路由和单页导航 ID 校验；两种可见文字记录 DOM 结构、无记录、非法时间和特殊字符；Markdown 结构与转义；YouTube 播放器适配的就绪、跳转、进度、销毁；现有 B 站与网页模式回归；Chrome Manifest V3 生产构建。人工验收至少覆盖有人工字幕、自动字幕、无文字记录、禁止嵌入的视频，及保存后在 Obsidian 阅读视图中的双向联动。禁止嵌入时应有清楚的不可播放提示，且不得把这种视频计为同等体验通过。

只在真实 Obsidian 验证通过后更新平台支持表、打包 Chrome 扩展与配套插件、附安装说明和校验和发布。安装包须包含运行所需的全部稳定文件，使用锁定依赖构建；继续保持公开仓库源码与 CI 可复现。全程使用代码、命令行和用户手动验收，不使用 Computer Use。

## 已知风险与边界

- YouTube 页面 DOM 会变；提取失败时保留视频信息保存能力，并要求用户手动打开文字记录后重试。只抓取当前页面已渲染出的字幕行；若面板虚拟滚动未完整渲染，应显示已抓取条数和「可能不完整」，不得宣称完整字幕。
- 一些视频禁止嵌入或受地区、年龄、登录状态限制。即使视频页可播放，也不保证 Obsidian 嵌入可播；发布前须明确用户可见的失败提示。
- 本版不下载视频文件、不提供无字幕语音转写、不保存评论、不支持 Shorts 专用流程，也不承诺与浏览器中已打开的 YouTube 播放器共用播放会话。

## 我注意到的取舍

- 你选择「稳定优先：读取页面显示的文字记录」，明确把可解释的采集结果放在覆盖率之前。
- 你要求「必须同等体验，验证通过再发布」，所以这里把笔记内播放和字幕双向联动写成发布条件。
